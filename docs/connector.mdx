The Databricks connector supports [automatic account provisioning and deprovisioning](/product/admin/account-provisioning).

<Note>
Workspace roles (such as **workspace-access** or **databricks-sql-access**) can only be granted to users, groups, and service principals that are already members of that workspace. If the request fails because the identity isn't a member, grant them membership in the workspace first, then request the role again.
</Note>

[This connector syncs non-human identities](/product/admin/nhi) and displays them on the **Identities overview** dashboard.

## Metastore access in C1

The connector syncs the Databricks [Unity Catalog](https://docs.databricks.com/aws/en/data-governance/unity-catalog/manage-privileges/privileges)
metastore as a C1 resource. Each privilege Databricks records on it
(`CREATE_CATALOG`, `READ_METADATA`, `USE_SHARE` and so on) becomes an
entitlement in C1, so you can review who holds it, request it, and revoke it
for users, groups and service principals. A grant held by a group is expandable
so C1 can resolve the group's members as holders. Ownership is shown as a
read-only `owner` entitlement — it cannot be granted or revoked through C1.

<Note>
The Metastores resource type is turned off by default. Turn it on from the connector's configuration page in C1.
</Note>

<Note>
**Notes on Unity Catalog access in C1:**

- Ownership is shown but cannot be provisioned. An owner that is not a Databricks account identity, such as a system account or a workspace admins group, is not shown at all.
- **MANAGE** and **ALL_PRIVILEGES** are not offered as entitlements, because Databricks rejects both at the metastore level.
- Unity Catalog tags are not synced.
</Note>

## Authentication methods

The connector authenticates with **OAuth** — an account-level service principal's client ID and secret. This is the only authentication method the connector supports.

## Gather Databricks credentials

Configuring the connector requires you to pass in credentials generated in Databricks. Gather these credentials before you move on.

<Warning>
A user with the **Account admin** role in each Databricks workspace you want to sync must perform this task.
</Warning>

Every step below happens in the Databricks **account console**. On AWS that is [https://accounts.cloud.databricks.com](https://accounts.cloud.databricks.com). Azure Databricks and Google Cloud Platform customers use their own account console host. When they configure the connector they only need the workspace **Hostname**; Account Hostname is optional.

### Look up your Databricks account ID

<Steps>
  <Step>
  Ensure that your Databricks user account has the **Account admin** role and is assigned to each Databricks workspace you want to sync to C1.
  </Step>
  <Step>
  In the Databricks account console, open the menu that appears next to your username in the upper right corner.
  </Step>
  <Step>
  Carefully copy and save the account ID.
  </Step>
</Steps>

### Create a service principal and an OAuth secret

The Databricks connector authenticates with OAuth, which syncs info from all Databricks workspaces the service principal can access.

<Steps>
  <Step>
  In the account console, go to **User management** > **Service principals** and click **Add service principal**. Give it a name you will recognize, such as `ConductorOne`.
  </Step>
  <Step>
  Open the new service principal, go to its **Secrets** tab, and generate an OAuth secret.

  Carefully copy and save the **Client ID** and **Secret**. The secret is shown only once.

  For the full walkthrough, see the [Databricks OAuth machine-to-machine documentation](https://docs.databricks.com/en/dev-tools/auth/oauth-m2m.html).
  </Step>
</Steps>

<Note>
There is no scope to pick in the console. The connector requests the `all-apis` scope itself when it exchanges the client ID and secret for a token, which covers the four API surfaces it reads: Unity Catalog, SCIM, access management and account provisioning.
</Note>

### Grant the service principal the roles it needs

<Steps>
  <Step>
  Make the service principal an account admin: in the account console, go to **User management** > **Service principals**, open the service principal, select its **Roles** tab, and enable **Account admin**.
  </Step>
  <Step>
  Assign it to each workspace you want C1 to sync, as an admin: in the account console, go to **Workspaces**, open the workspace, select **Permissions**, click **Add permissions**, select the service principal, and choose **Admin**. Assign **Admin** directly to the service principal — the connector does not treat Admin inherited through a group as enough.

  Repeat this for every workspace you want synced. Workspace **Admin** is enough to read Unity Catalog privileges on a metastore reached through that workspace. If the metastore's workspaces are not synced, make the service principal the **Metastore Admin** instead: in the account console, go to **Catalog**, open the metastore, and set **Metastore Admin** to the service principal's application ID.
  </Step>
</Steps>

<Warning>
Without this, the metastore sync fails with a permission error naming the metastore. Databricks returns a partial privilege list rather than an error, and C1 would treat the missing grants as revoked.
</Warning>

**Done.** Here's the set of credentials you'll need when setting up the connector:

- Account ID
- OAuth client ID
- OAuth client secret

Next, move on to the instructions for your chosen setup method.

## Configure the Databricks connector

<Warning>
To complete this task, you'll need:

- The **Connector Administrator** or **Super Administrator** role in C1
- Access to the set of Databricks credentials generated by following the instructions above
</Warning>

<Tabs>
<Tab title="Cloud-hosted">

**Follow these instructions to use a built-in, no-code connector hosted by C1.**

<Steps>
  <Step>
  In C1, navigate to **Apps** > **Connectors** and click **Add connector**.
  </Step>
  <Step>
  Search for **Databricks** and click **Add**.
  </Step>
  <Step>
  Choose where to add the connector: **Create a new app**, or **Add to an existing app** (then select the app).

  If you're creating a new app, choose whether to link it to an application discovered from your identity provider: select **Yes** and pick the IdP application, or **No** to continue with just the connector.
  </Step>
  <Step>
  Set the connector's **Name** and, optionally, a **Description**.
  </Step>
  <Step>
  Click the pencil icon next to **Owners** to choose who can configure and manage this connector.
  </Step>
  <Step>
  Click **Add**. The connector is created and its configuration page opens.
  </Step>
  <Step>
  Find the **Settings** area of the page and click **Edit**.
  </Step>
  <Step>
  Paste the account ID you looked up in Step 1 into the **Account ID** field.
  </Step>
  <Step>
  Enter your OAuth client ID and client secret into the **OAuth2 Client ID** and **OAuth2 Client Secret** fields.
  </Step>
  <Step>
  Optionally, narrow what the connector syncs:

    - **Workspaces**: limit the sync to these workspaces, by workspace name, deployment name, or numeric workspace ID.
    - **Exclude Workspaces**: workspaces to leave out of the sync, by workspace name, deployment name, or numeric workspace ID.

  Fill in **Workspaces** or **Exclude Workspaces**, not both.
  </Step>
  <Step>
  **Google Cloud Platform and Azure Databricks customers only:** Enter your Databricks workspace hostname in the **Hostname** field. Account Hostname is optional: the connector derives it from Hostname when unset.
    - For more on how to look up these values for GCP, see the GCP Databricks [REST API reference](https://docs.databricks.com/api/gcp/account/introduction) and [identifiers for workspace objects](https://docs.gcp.databricks.com/en/workspace/workspace-details.html) documentation.
    - For more on how to look up these values for Azure Databricks, see the the Azure Databricks [REST API reference](https://docs.databricks.com/api/azure/account/introduction) and [identifiers for workspace objects](https://learn.microsoft.com/en-us/azure/databricks/workspace/workspace-details) documentation.
  </Step>

  <Step>
  Click **Save**.
  </Step>
  <Step>
  The connector's label changes to **Syncing**, followed by **Connected**. You can view the logs to ensure that information is syncing.
  </Step>
</Steps>

**Done.** Your Databricks connector is now pulling access data into C1.

</Tab>

### Step 2: Create Kubernetes configuration files

Create two Kubernetes manifest files for your Databricks connector deployment:

#### Secrets configuration

```yaml expandable
# baton-databricks-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: baton-databricks-secrets
type: Opaque
stringData:
  # C1 credentials
  BATON_CLIENT_ID: <C1 client ID>
  BATON_CLIENT_SECRET: <C1 client secret>
  
  # Databricks account ID (required for both credential options below)
  BATON_ACCOUNT_ID: <Databricks account ID>

  # Databricks credentials: OAuth
  BATON_DATABRICKS_CLIENT_ID: <OAuth client ID>
  BATON_DATABRICKS_CLIENT_SECRET: <OAuth client secret>

  # Optional: limit the sync to specific workspaces
  # (workspace name, deployment name, or numeric ID).
  # Mutually exclusive with BATON_DATABRICKS_EXCLUDE_WORKSPACES — set one or the other, never both.
  # BATON_WORKSPACES: <workspace-a,workspace-b>

  # Optional: exclude specific workspaces from the sync
  # (workspace name, deployment name, or numeric ID).
  # Mutually exclusive with BATON_WORKSPACES — set one or the other, never both.
  BATON_DATABRICKS_EXCLUDE_WORKSPACES: <workspace-a,workspace-b>

  # Optional: include if you want C1 to provision access using this connector
  BATON_PROVISIONING: true
```

<Warning>
**`BATON_WORKSPACES` and `BATON_DATABRICKS_EXCLUDE_WORKSPACES` cannot both be set.** They are mutually exclusive, and a config carrying both is rejected at startup before any API call. Choose one.
</Warning>

<Note>
OAuth requires a reachable account API. If the account API check fails at startup, the connector fails validation instead of falling back to a workspace-only sync, even when `BATON_WORKSPACES` is set.
</Note>

<Note>
**Accounts with many workspaces:** to decide which metastore each workspace serves, the connector may list a workspace's catalogs, and it holds one such listing per workspace while it runs — so a wider account needs a larger buffer. The 5 MB default suits about ten workspaces with a few hundred catalogs each. Above that the connector re-reads listings it has already fetched, which lengthens the sync and uses more of your Databricks API rate limit. Set `BATON_HTTP_CACHE_MAX_SIZE` to a larger number of megabytes in the Secret above.
</Note>

See the connector's README or run `--help` to see all available configuration flags and environment variables.

#### Deployment configuration

```yaml expandable
# baton-databricks.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: baton-databricks
  labels:
    app: baton-databricks
spec:
  selector:
    matchLabels:
      app: baton-databricks
  template:
    metadata:
      labels:
        app: baton-databricks
        baton: true
        baton-app: databricks
    spec:
      containers:
      - name: baton-databricks
        image: public.ecr.aws/conductorone/baton-databricks:latest
        imagePullPolicy: IfNotPresent
        env:
        - name: BATON_HOST_ID
          value: baton-databricks
        envFrom:
        - secretRef:
            name: baton-databricks-secrets
```

### Step 3: Deploy the connector

<Steps>
  <Step>
  Create a namespace in which to run C1 connectors (if desired), then apply the secret config and deployment config files.
  </Step>
  <Step>
  Check that the connector data uploaded correctly. In C1, click **Apps**. On the **Managed apps** tab, locate and click the name of the application you added the Databricks connector to. Databricks data should be found on the **Entitlements** and **Accounts** tabs.
  </Step>
</Steps>

**Done.** Your Databricks connector is now pulling access data into C1.
