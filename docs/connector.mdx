The Databricks connector supports [automatic account provisioning and deprovisioning](/product/admin/account-provisioning).

<Note>
Workspace roles (such as **workspace-access** or **databricks-sql-access**) can only be granted to users, groups, and service principals that are already members of that workspace. If the request fails because the identity isn't a member, grant them membership in the workspace first, then request the role again.

Revoking the workspace **member** entitlement removes the principal's entire workspace assignment. If the principal is also a workspace admin, their admin access to that workspace is removed too. This also applies to groups: revoking the workspace **member** entitlement from a group removes the group's entire workspace assignment, including admin access if the group is a workspace admin (its members lose it).
</Note>

[This connector syncs non-human identities](/product/admin/nhi) and displays them on the **Identities overview** dashboard.

### Connector actions

Connector actions are custom capabilities that extend C1 automations with app-specific operations. Use the [Account lifecycle action](/product/admin/automations-steps-reference#account-lifecycle-action) automation step to run `enable_user` and `disable_user`. The Databricks actions don't appear under **Perform connector action**.

| Automation step | Actions offered | How the target is selected |
|-----------------|-----------------|----------------------------|
| Account lifecycle action | `enable_user`, `disable_user` | The step's own target-account selector — either the account in context or a specific account. C1 resolves `user_id` from that account. |

| Action name | Additional fields | Description |
|-------------|-------------------|-------------|
| `enable_user` | `user_id` (string, required) | Reactivates a Databricks account user. |
| `disable_user` | `user_id` (string, required) | Deactivates a Databricks account user. |

<Note>
These actions act on the account-level user, so disabling a user blocks them in the Databricks account and in every workspace. Only the user's active status changes: their permissions and memberships are kept, so enabling the user restores the same access. Running an action on a user who is already in the target state succeeds. Databricks can take a few minutes to apply the change, so a sync that runs sooner can still show the previous status. Account provisioning doesn't reactivate an inactive user; run `enable_user` instead.

The service principal that runs these actions needs the **Account admin** role. Without it, Databricks rejects the request with "This API is disabled for users without account admin status" and the action fails with a permission error.

The `user_id` value is the user's Databricks account user ID: a string of digits, such as `1234567890123456`. The actions reject usernames, email addresses, and any value that contains a character other than 0-9 with the error "user ID must contain only digits 0-9". An ID that belongs to a group or service principal, or that does not exist, returns a not-found error. Databricks ignores leading zeros, so `0001234567890123456` acts on the same user as `1234567890123456`. Within a C1 automation, C1 fills this value from the target account.
</Note>

## Metastore, catalog and schema access in C1

The connector syncs Databricks [Unity Catalog](https://docs.databricks.com/aws/en/data-governance/unity-catalog/manage-privileges/privileges)
metastores, the catalogs in them, and the schemas in those catalogs as C1 resources. Each privilege Databricks
records on one of them (`CREATE_CATALOG` on a metastore, `USE_CATALOG` or
`SELECT` on a catalog, `USE_SCHEMA` on a schema, and so on) becomes an entitlement in C1, so you can
review who holds it, request it, and revoke it for users, groups and service
principals. A grant held by a group is expandable so C1 can resolve the
group's members as holders. Ownership is shown as a read-only `owner`
entitlement — it cannot be granted or revoked through C1.

<Note>
The Metastores, Catalogs and Schemas resource types are turned off by default. Turn on the ones you want from the connector's configuration page in C1. Catalogs sync under their metastore and schemas under their catalog, so turn on every level above the one you want; turning on Catalogs alone, or Schemas without Catalogs, syncs nothing. They all use the same OAuth credentials; no additional configuration fields are needed.
</Note>

<Note>
**Notes on Unity Catalog access in C1:**

- Ownership is shown but cannot be provisioned. An owner that is not a Databricks account identity, such as a system account or a workspace admins group, is not shown at all.
- Metastore privileges held by a workspace's built-in admins group, and that group's members, are shown as read-only grants when the workspace is in the sync scope. The group appears as `admins (<workspace name>)`. C1 can't grant or revoke either, and Databricks doesn't allow a revoked privilege to be granted back to this group. Manage both in Databricks.
- **MANAGE** and **ALL_PRIVILEGES** are not offered on a metastore, because Databricks rejects both at that level.
- A catalog is synced when any running workspace in scope attached to its metastore lists it, and the same catalog name is kept once per metastore. A catalog that only excluded workspaces can reach is not synced.
- The built-in `system` catalog is never synced, and neither is any other catalog Databricks marks as a system catalog, whoever owns it.
- `information_schema` is skipped in every catalog. Databricks creates it read-only and its privileges cannot be granted.
- If a catalog becomes unreachable, access requests can fail until the connector can distinguish deletion from a binding or visibility change. Catalog ownership or **MANAGE** alone cannot prove deletion; that check requires the **Metastore Admin**.
- Unity Catalog tags are not synced.
</Note>

## Authentication methods

The connector authenticates as an account-level service principal, named by its client ID. It proves it is that service principal in one of three ways:

- **OAuth client secret** (default): the service principal's client ID and secret.
- **Workload identity federation**: the connector presents an externally issued JWT that identifies the workload, such as a SPIFFE JWT-SVID or a Kubernetes projected service account token, and Databricks exchanges it for a short-lived token. No long-lived secret is stored, and the Databricks administrator controls access through a service principal federation policy. This fits a deployment where the platform running the connector already issues it a workload identity token.
- **Workload identity federation (C1-hosted)**: C1 signs a short-lived JWT for this connector, and Databricks exchanges it for a short-lived token. No credential is stored, and the hosted runtime selects this method.

The authentication method selects the credential. There is no personal access token (PAT), workspace token, or username and password option.

<Warning>
The token file method is for a connector you run yourself, on the command line or in service mode. Select it with `--auth-method workload-identity-file`. A C1-hosted connector uses workload identity too, but C1 issues the JWT and the runtime selects the method.
</Warning>

### Optional: faster updates between syncs

By default, the Databricks connector picks up access changes on its regular sync schedule. You can optionally turn on incremental sync, which checks Databricks' activity log between full syncs so that changes like new group members, new service principals, and admin role changes on service principals show up in C1 sooner. Full syncs still run as usual and remain the source of truth. Removed group memberships are picked up incrementally too, but deleted users, groups, and service principals are only reflected after the next full sync.

Role assignments that Databricks stores in access-control rule sets are also only reflected after the next full sync. These are group roles such as group manager, service principal roles, and the account `marketplace.admin` role.

Incremental sync is turned on by providing the ID of a Databricks SQL warehouse (the **SQL Warehouse ID** setting, `BATON_SQL_WAREHOUSE_ID`) and turned off by leaving it empty — there is no separate on/off switch. Ask your connector operator or C1 support contact to enable it for you.

#### Incremental sync requirements

Your Databricks account must meet all of the following:

- **Unity Catalog.** The SQL warehouse must be in a workspace enabled for Unity Catalog, and the metastore must be on Unity Catalog Privilege Model Version 1.0. Databricks enables most workspaces created after November 2023 for Unity Catalog automatically.
- **System tables.** The connector reads Databricks' audit log system table, `system.access.audit`. Databricks currently offers this table as a Public Preview.
- **A SQL warehouse, preferably serverless.** You don't need to create a new one: Databricks creates a **Starter Warehouse** in each workspace automatically, and any SQL warehouse works. See the recommendation below about the warehouse type.
- **Permissions for the connector's service principal**, in addition to the **Account admin** role it already needs:
  - `USE CATALOG` on the `system` catalog
  - `USE SCHEMA` and `SELECT` on the `system.access` schema
  - **Can use** on the SQL warehouse

<Note>
**We recommend a serverless SQL warehouse.** It starts in seconds, while a pro or classic warehouse can take several minutes to start. The connector waits up to about 6 minutes for the warehouse to start and each query to finish, so a slower start can delay updates until the next one. Serverless SQL warehouses require the Premium plan or above.
</Note>

<Warning>
**Incremental sync covers one cloud region.** Databricks keeps workspace activity in the audit log of the region where each workspace is deployed. The connector only receives incremental updates for workspaces in the same region as the SQL warehouse. Workspaces in other regions are still updated by full syncs.
</Warning>

#### Set up incremental sync

<Warning>
A Databricks user with the **Account admin** role, and the **Metastore admin** role or the right to grant access to the `system` catalog, must perform this task.
</Warning>

<Steps>
  <Step>
  Choose a SQL warehouse in a Unity Catalog-enabled workspace, in the same region as the workspaces you want to update incrementally. In that workspace, go to **SQL Warehouses**, open the warehouse, and copy its ID. Check its type: if it isn't **Serverless**, switch it to serverless if your plan allows it (see the recommendation above).
  </Step>
  <Step>
  On the **SQL Warehouses** page, click the kebab menu (three-dot icon) next to the warehouse, click **Permissions**, and give the connector's service principal the **Can use** permission.
  </Step>
  <Step>
  In the same workspace, run the following in the SQL editor, replacing `<application-id>` with the service principal's application (client) ID:

  ```sql
  GRANT USE CATALOG ON CATALOG system TO `<application-id>`;
  GRANT USE SCHEMA, SELECT ON SCHEMA system.access TO `<application-id>`;
  ```
  </Step>
  <Step>
  Enter the warehouse ID in the connector's **SQL Warehouse ID** setting (`BATON_SQL_WAREHOUSE_ID`).
  </Step>
</Steps>

The SQL warehouse can live in any workspace in that region that is not listed in **Exclude Workspaces**, including a workspace outside **Workspaces** — the connector finds it automatically. **Workspaces** and **Exclude Workspaces** also limit which workspaces incremental sync updates, as they do for full syncs. Changes reach C1 roughly four hours after they happen: Databricks delivers audit log entries with a delay, so the connector waits before reading them.

<Note>
The incremental sync setup isn't checked when the connector starts, so a problem with it never blocks full syncs or provisioning. If something is missing, such as a permission or a warehouse that can't be found, every incremental update fails and the connector logs an error that names the cause until you fix it.
</Note>

## Gather Databricks credentials

Configuring the connector requires you to pass in credentials generated in Databricks. Gather these credentials before you move on.

<Note>
A user with the **Account admin** role in your Databricks account must perform this task. Account admin is an account-level role, managed in the Databricks account console.
</Note>

Every step below happens in the Databricks **account console**. On AWS that is [https://accounts.cloud.databricks.com](https://accounts.cloud.databricks.com). Azure Databricks and Google Cloud Platform customers use their own account console host. When they configure the connector they only need their Databricks domain in **Hostname**; Account Hostname is optional.

### Look up your Databricks account ID

<Steps>
  <Step>
  Log in to the Databricks account console with a user that has the **Account admin** role.
  </Step>
  <Step>
  In the Databricks account console, open the menu that appears next to your username in the upper right corner.
  </Step>
  <Step>
  Carefully copy and save the account ID.
  </Step>
</Steps>

### Create a service principal and an OAuth secret

The Databricks connector authenticates as a service principal, which syncs info from all Databricks workspaces that service principal can access.

<Steps>
  <Step>
  In the account console, go to **User management** > **Service principals** and click **Add service principal**. Give it a name you will recognize, such as `ConductorOne`.
  </Step>
  <Step>
  Open the new service principal, go to its **Secrets** tab, and generate an OAuth secret.

  Carefully copy and save the **Client ID** and **Secret**. The secret is shown only once.

  For the full walkthrough, see the [Databricks OAuth machine-to-machine documentation](https://docs.databricks.com/en/dev-tools/auth/oauth-m2m.html).
  </Step>
  <Step>
  Give the service principal the **Account admin** role: in the account console, go to **User management** > **Service principals**, click the service principal, and on the **Roles** tab select **Account admin**. Databricks requires this role for any service principal that calls account-level APIs, and the connector fails validation without it.
  </Step>
</Steps>

<Note>
There is no scope to pick in the console. The connector requests the `all-apis` scope itself when it exchanges the client ID and secret for a token, which covers the four API surfaces it reads: Unity Catalog, SCIM, access management and account provisioning.
</Note>

### Grant the service principal the roles it needs

<Steps>
  <Step>
  Make the service principal an account admin: in the account console, go to **User management** > **Service principals**, open the service principal, select its **Roles** tab, and enable **Account admin**.
  </Step>
  <Step>
  Assign it to each workspace you want C1 to sync, as an admin: in the account console, go to **Workspaces**, open the workspace, select **Permissions**, click **Add permissions**, select the service principal, and choose **Admin**. Assign **Admin** directly to the service principal — the connector does not treat Admin inherited through a group as enough.

  Repeat this for every workspace you want synced. Workspace **Admin** is enough to read Unity Catalog privileges on a metastore reached through that workspace. If the service principal can't be assigned Admin directly on a synced workspace attached to the metastore, make it the **Metastore Admin** instead: in the account console, go to **Catalog**, open the metastore, and set **Metastore Admin** to the service principal's application ID. A metastore with no synced workspace attached is left out either way.
  </Step>
</Steps>

<Warning>
Without workspace **Admin** or **Metastore Admin**, the metastore sync fails with a permission error naming the metastore. Databricks shows a caller only the grants it is allowed to see, so reporting that shorter list would make C1 treat the rest as revoked.
</Warning>

### Let the service principal read catalog privileges

Skip this section if you are not syncing catalogs, or if the service principal is already the **Metastore Admin**. Databricks shows a catalog's full privilege list only to the metastore admin, the service principal that owns the catalog itself, or a holder of **MANAGE** on it. The connector matches ownership against the service principal itself, so a catalog owned by a group it belongs to does not count. **Admin** assigned directly to the service principal on a workspace is enough only when the catalog is owned by that workspace's admins group (`_workspace_admins_<workspace>_<workspace id>`).

Otherwise, grant **MANAGE** and **USE CATALOG** on each catalog you want synced. **MANAGE** alone is not enough: Databricks does not return a catalog at all unless the caller is the metastore admin, owns it, or holds **USE CATALOG** on it, and a catalog it does not return is one C1 removes.

<Steps>
  <Step>
  In the workspace, open **Catalog Explorer** and open the catalog.
  </Step>
  <Step>
  Select **Permissions**, then click **Grant**.
  </Step>
  <Step>
  Select the service principal, check **MANAGE** and **USE CATALOG**, and confirm.
  </Step>
</Steps>

<Warning>
For a discovered catalog that is not excluded by the system-catalog rule above, missing these permissions fails the sync naming that catalog. Databricks would otherwise return only the privileges the caller can see, and reporting that short list would make C1 delete the grants it cannot read. Failing keeps what C1 already has.

The connector asks every running workspace in scope attached to the metastore, so a catalog bound to one of those workspaces is included. A catalog the service principal cannot see on any of them is not, and C1 removes it and its grants.

If the service principal cannot list catalogs at all through one of those workspaces, the connector cannot tell which catalogs are there, so the sync fails naming the metastore and that workspace instead of removing the catalogs it could not list. Give the service principal **Admin** on that workspace, or leave that workspace out with **Workspaces** or **Exclude Workspaces**.
</Warning>

### Let the service principal list schemas and read their privileges

Skip this section if you are not syncing schemas, or if the service principal owns the metastore or the catalog.

Workspace **Admin** does not list every schema, except when the catalog is owned by the workspace admins group (`_workspace_admins_<workspace>_<id>`) and the service principal is a direct Admin of that workspace. On any other catalog the service principal does not own, Databricks returns only the schemas it owns or can use, with HTTP 200. To list every schema, the service principal must own the metastore, own the catalog, be that direct Admin, or hold **MANAGE**, **USE SCHEMA**, or **ALL PRIVILEGES** on the catalog.

Listing the schemas is not the same as reading who holds what on them. For a schema's full privilege list, and to grant or revoke a schema privilege, the service principal must own the metastore, the catalog or the schema, hold **MANAGE** on the schema or on the catalog above it, or be that direct Admin. **USE SCHEMA** and **ALL PRIVILEGES** list every schema and do not read their privileges, because Databricks leaves **MANAGE** out of **ALL PRIVILEGES**. A service principal given only **USE SCHEMA** gets its schemas synced and then a permission error on their grants, so grant **MANAGE** on the catalog to cover both.

<Warning>
A catalog whose schemas cannot all be listed fails the sync, and so does a schema whose privilege list cannot be proved complete, named in the error. System catalogs are never synced, whoever owns them, so their schemas are not synced either.
</Warning>

**Done.** Here's the set of credentials you'll need when setting up the connector:

- Account ID
- OAuth client ID
- OAuth client secret

### Use workload identity federation instead of a secret

You can skip the OAuth secret and have the connector present an externally issued JWT instead. The connector must be able to read that JWT where it runs, so this suits a deployment whose platform injects a workload identity token.

<Steps>
  <Step>
  Create the service principal as described above, but do not generate an OAuth secret.
  </Step>
  <Step>
  Follow the [Databricks OAuth token federation documentation](https://docs.databricks.com/aws/en/dev-tools/auth/oauth-federation-exchange) to add a service principal federation policy that trusts the issuer, subject and audience of the JWT your workload receives.
  </Step>
  <Step>
  Make the JWT available to the connector, ideally as a file that your platform rotates.
  </Step>
</Steps>

**Done.** In this case the credentials are the account ID, the OAuth client ID, and the JWT, in place of the OAuth client secret.

#### C1-hosted connectors

A C1-hosted connector needs no JWT from you. C1 signs one for the connector, valid for 10 minutes, and your tenant needs the `WORKLOAD_IDENTITY_OIDC_ISSUER` feature flag. Add a federation policy to the service principal with these values:

| Policy value | Value |
| --- | --- |
| Issuer | `<tenant endpoint>/auth/v1/workload-identity`. C1 publishes its keys at `<tenant endpoint>/auth/v1/workload-identity/.well-known/openid-configuration`, so Databricks can discover them. |
| Audience | The service principal's OAuth client ID. |
| Subject | `c1:tenant/<tenant id>/app/<app id>/connector/<connector id>`. Use it to limit the policy to one connector. |

Next, move on to the instructions for your chosen setup method.

### Step 2: Create Kubernetes configuration files

Create two Kubernetes manifest files for your Databricks connector deployment:

#### Secrets configuration

```yaml expandable
# baton-databricks-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: baton-databricks-secrets
type: Opaque
stringData:
  # C1 credentials
  BATON_CLIENT_ID: <C1 client ID>
  BATON_CLIENT_SECRET: <C1 client secret>
  
  # Databricks account ID (required)
  BATON_ACCOUNT_ID: <Databricks account ID>

  # Databricks credentials: OAuth
  BATON_DATABRICKS_CLIENT_ID: <OAuth client ID>
  BATON_DATABRICKS_CLIENT_SECRET: <OAuth client secret>

  # Alternative to BATON_DATABRICKS_CLIENT_SECRET: workload identity federation.
  # Both variables below are required together. Without BATON_AUTH_METHOD the
  # connector validates against the client secret method and fails on the
  # missing secret.
  # Point the file at a projected service account token, or any other externally
  # issued JWT your federation policy trusts. It is read again on every token
  # refresh, so a rotated token needs no restart.
  # Nothing creates this file for you: uncomment the matching volume and
  # volumeMount in the Deployment below, or mount the JWT there yourself.
  # BATON_AUTH_METHOD: workload-identity-file
  # BATON_DATABRICKS_OIDC_TOKEN_FILE: /var/run/secrets/databricks/token

  # Optional: limit the sync to specific workspaces
  # (workspace name, deployment name, or numeric ID).
  # Also scopes which metastores sync: narrowing it removes metastores that no listed workspace is attached to.
  # Mutually exclusive with BATON_DATABRICKS_EXCLUDE_WORKSPACES — set one or the other, never both.
  # BATON_WORKSPACES: <workspace-a,workspace-b>

  # Optional: exclude specific workspaces from the sync
  # (workspace name, deployment name, or numeric ID).
  # Mutually exclusive with BATON_WORKSPACES — set one or the other, never both.
  # BATON_DATABRICKS_EXCLUDE_WORKSPACES: <workspace-a,workspace-b>

  # Optional: setting this enables incremental sync; leave it unset to disable it.
  # ID of the SQL warehouse used to query the system.access.audit log between full syncs.
  # BATON_SQL_WAREHOUSE_ID: <SQL warehouse ID>

  # Optional: include if you want C1 to provision access using this connector
  BATON_PROVISIONING: true
```

<Warning>
**`BATON_WORKSPACES` and `BATON_DATABRICKS_EXCLUDE_WORKSPACES` cannot both be set.** They are mutually exclusive, and a config carrying both is rejected at startup before any API call. Choose one.
</Warning>

<Note>
Both credential options require a reachable account API. If the account API check fails at startup, the connector fails validation instead of falling back to a workspace-only sync, even when `BATON_WORKSPACES` is set.
</Note>

See the connector's README or run `--help` to see all available configuration flags and environment variables.
