The Databricks connector supports [automatic account provisioning and deprovisioning](/product/admin/account-provisioning).

<Note>
Workspace roles (such as **workspace-access** or **databricks-sql-access**) can only be granted to users, groups, and service principals that are already members of that workspace. If the request fails because the identity isn't a member, grant them membership in the workspace first, then request the role again.

Revoking the workspace **member** entitlement removes the principal's entire workspace assignment. If the principal is also a workspace admin, their admin access to that workspace is removed too. This also applies to groups: revoking the workspace **member** entitlement from a group removes the group's entire workspace assignment, including admin access if the group is a workspace admin (its members lose it).
</Note>

[This connector syncs non-human identities](/product/admin/nhi) and displays them on the **Identities overview** dashboard.

## Metastore access in C1

The connector syncs the Databricks [Unity Catalog](https://docs.databricks.com/aws/en/data-governance/unity-catalog/manage-privileges/privileges)
metastore as a C1 resource. Each privilege Databricks records on it
(`CREATE_CATALOG`, `READ_METADATA`, `USE_SHARE` and so on) becomes an
entitlement in C1, so you can review who holds it, request it, and revoke it
for users, groups and service principals. A grant held by a group is expandable
so C1 can resolve the group's members as holders. Ownership is shown as a
read-only `owner` entitlement — it cannot be granted or revoked through C1.

<Note>
The Metastores resource type is turned off by default. Turn it on from the connector's configuration page in C1.
</Note>

<Note>
**Notes on Unity Catalog access in C1:**

- Ownership is shown but cannot be provisioned. An owner that is not a Databricks account identity, such as a system account or a workspace admins group, is not shown at all.
- **MANAGE** and **ALL_PRIVILEGES** are not offered as entitlements, because Databricks rejects both at the metastore level.
- Unity Catalog tags are not synced.
</Note>

## Authentication methods

The connector authenticates with **OAuth** — an account-level service principal's client ID and secret. This is the only authentication method the connector supports.

### Optional: faster updates between syncs

By default, the Databricks connector picks up access changes on its regular sync schedule. You can optionally turn on incremental sync, which checks Databricks' activity log between full syncs so that changes like new group members show up in C1 sooner. Full syncs still run as usual and remain the source of truth. Removed group memberships are picked up incrementally too, but deleted users, groups, and service principals are only reflected after the next full sync.

Role assignments that Databricks stores in access-control rule sets are also only reflected after the next full sync. These are group roles such as group manager, service principal roles, and the account `marketplace.admin` role.

Incremental sync is turned on by providing the ID of a Databricks SQL warehouse (the **SQL Warehouse ID** setting, `BATON_SQL_WAREHOUSE_ID`) and turned off by leaving it empty — there is no separate on/off switch. Ask your connector operator or C1 support contact to enable it for you.

#### Incremental sync requirements

Your Databricks account must meet all of the following:

- **Unity Catalog.** The SQL warehouse must be in a workspace enabled for Unity Catalog, and the metastore must be on Unity Catalog Privilege Model Version 1.0. Databricks enables most workspaces created after November 2023 for Unity Catalog automatically.
- **System tables.** The connector reads Databricks' audit log system table, `system.access.audit`. Databricks currently offers this table as a Public Preview.
- **A SQL warehouse, preferably serverless.** You don't need to create a new one: Databricks creates a **Starter Warehouse** in each workspace automatically, and any SQL warehouse works. See the recommendation below about the warehouse type.
- **Permissions for the connector's service principal**, in addition to the **Account admin** role it already needs:
  - `USE CATALOG` on the `system` catalog
  - `USE SCHEMA` and `SELECT` on the `system.access` schema
  - **Can use** on the SQL warehouse

<Note>
**We recommend a serverless SQL warehouse.** It starts in seconds, while a pro or classic warehouse can take several minutes to start. The connector waits up to about 6 minutes for the warehouse to start and each query to finish, so a slower start can delay updates until the next one. Serverless SQL warehouses require the Premium plan or above.
</Note>

<Warning>
**Incremental sync covers one cloud region.** Databricks keeps workspace activity in the audit log of the region where each workspace is deployed. The connector only receives incremental updates for workspaces in the same region as the SQL warehouse. Workspaces in other regions are still updated by full syncs.
</Warning>

#### Set up incremental sync

<Warning>
A Databricks user with the **Account admin** role, and the **Metastore admin** role or the right to grant access to the `system` catalog, must perform this task.
</Warning>

<Steps>
  <Step>
  Choose a SQL warehouse in a Unity Catalog-enabled workspace, in the same region as the workspaces you want to update incrementally. In that workspace, go to **SQL Warehouses**, open the warehouse, and copy its ID. Check its type: if it isn't **Serverless**, switch it to serverless if your plan allows it (see the recommendation above).
  </Step>
  <Step>
  On the **SQL Warehouses** page, click the kebab menu (three-dot icon) next to the warehouse, click **Permissions**, and give the connector's service principal the **Can use** permission.
  </Step>
  <Step>
  In the same workspace, run the following in the SQL editor, replacing `<application-id>` with the service principal's application (client) ID:

  ```sql
  GRANT USE CATALOG ON CATALOG system TO `<application-id>`;
  GRANT USE SCHEMA, SELECT ON SCHEMA system.access TO `<application-id>`;
  ```
  </Step>
  <Step>
  Enter the warehouse ID in the connector's **SQL Warehouse ID** setting (`BATON_SQL_WAREHOUSE_ID`).
  </Step>
</Steps>

The SQL warehouse can live in any workspace in that region that is not listed in **Exclude Workspaces**, including a workspace outside **Workspaces** — the connector finds it automatically. **Workspaces** and **Exclude Workspaces** also limit which workspaces incremental sync updates, as they do for full syncs. Changes reach C1 roughly four hours after they happen: Databricks delivers audit log entries with a delay, so the connector waits before reading them.

<Note>
The incremental sync setup isn't checked when the connector starts, so a problem with it never blocks full syncs or provisioning. If something is missing, such as a permission or a warehouse that can't be found, every incremental update fails and the connector logs an error that names the cause until you fix it.
</Note>

## Gather Databricks credentials

Configuring the connector requires you to pass in credentials generated in Databricks. Gather these credentials before you move on.

<Warning>
A user with the **Account admin** role in your Databricks account must perform this task. Account admin is an account-level role, managed in the Databricks account console.
</Warning>

Every step below happens in the Databricks **account console**. On AWS that is [https://accounts.cloud.databricks.com](https://accounts.cloud.databricks.com). Azure Databricks and Google Cloud Platform customers use their own account console host. When they configure the connector they only need their Databricks domain in **Hostname**; Account Hostname is optional.

### Look up your Databricks account ID

<Steps>
  <Step>
  Log in to the Databricks account console with a user that has the **Account admin** role.
  </Step>
  <Step>
  In the Databricks account console, open the menu that appears next to your username in the upper right corner.
  </Step>
  <Step>
  Carefully copy and save the account ID.
  </Step>
</Steps>

### Create a service principal and an OAuth secret

The Databricks connector authenticates with OAuth, which syncs info from all Databricks workspaces the service principal can access.

<Steps>
  <Step>
  In the account console, go to **User management** > **Service principals** and click **Add service principal**. Give it a name you will recognize, such as `ConductorOne`.
  </Step>
  <Step>
  Open the new service principal, go to its **Secrets** tab, and generate an OAuth secret.

  Carefully copy and save the **Client ID** and **Secret**. The secret is shown only once.

  For the full walkthrough, see the [Databricks OAuth machine-to-machine documentation](https://docs.databricks.com/en/dev-tools/auth/oauth-m2m.html).
  </Step>
  <Step>
  Give the service principal the **Account admin** role: in the account console, go to **User management** > **Service principals**, click the service principal, and on the **Roles** tab select **Account admin**. Databricks requires this role for any service principal that calls account-level APIs, and the connector fails validation without it.
  </Step>
</Steps>

<Note>
There is no scope to pick in the console. The connector requests the `all-apis` scope itself when it exchanges the client ID and secret for a token, which covers the four API surfaces it reads: Unity Catalog, SCIM, access management and account provisioning.
</Note>

### Grant the service principal the roles it needs

<Steps>
  <Step>
  Make the service principal an account admin: in the account console, go to **User management** > **Service principals**, open the service principal, select its **Roles** tab, and enable **Account admin**.
  </Step>
  <Step>
  Assign it to each workspace you want C1 to sync, as an admin: in the account console, go to **Workspaces**, open the workspace, select **Permissions**, click **Add permissions**, select the service principal, and choose **Admin**. Assign **Admin** directly to the service principal — the connector does not treat Admin inherited through a group as enough.

  Repeat this for every workspace you want synced. Workspace **Admin** is enough to read Unity Catalog privileges on a metastore reached through that workspace. If the service principal can't be assigned Admin directly on a synced workspace attached to the metastore, make it the **Metastore Admin** instead: in the account console, go to **Catalog**, open the metastore, and set **Metastore Admin** to the service principal's application ID. A metastore with no synced workspace attached is left out either way.
  </Step>
</Steps>

<Warning>
Without this, the metastore sync fails with a permission error naming the metastore. Databricks returns a partial privilege list rather than an error, and C1 would treat the missing grants as revoked.
</Warning>

**Done.** Here's the set of credentials you'll need when setting up the connector:

- Account ID
- OAuth client ID
- OAuth client secret

Next, move on to the instructions for your chosen setup method.

## Configure the Databricks connector

<Warning>
To complete this task, you'll need:

- The **Connector Administrator** or **Super Administrator** role in C1
- Access to the set of Databricks credentials generated by following the instructions above
</Warning>

<Tabs>
<Tab title="Cloud-hosted">

**Follow these instructions to use a built-in, no-code connector hosted by C1.**

<Steps>
  <Step>
  In C1, navigate to **Apps** > **Connectors** and click **Add connector**.
  </Step>
  <Step>
  Search for **Databricks** and click **Add**.
  </Step>
  <Step>
  Choose where to add the connector: **Create a new app**, or **Add to an existing app** (then select the app).

  If you're creating a new app, choose whether to link it to an application discovered from your identity provider: select **Yes** and pick the IdP application, or **No** to continue with just the connector.
  </Step>
  <Step>
  Set the connector's **Name** and, optionally, a **Description**.
  </Step>
  <Step>
  Click the pencil icon next to **Owners** to choose who can configure and manage this connector.
  </Step>
  <Step>
  Click **Add**. The connector is created and its configuration page opens.
  </Step>
  <Step>
  Find the **Settings** area of the page and click **Edit**.
  </Step>
  <Step>
  Paste the account ID you looked up in Step 1 into the **Account ID** field.
  </Step>
  <Step>
  Enter your OAuth client ID and client secret into the **OAuth2 Client ID** and **OAuth2 Client Secret** fields.
  </Step>
  <Step>
  Optionally, narrow what the connector syncs:

    - **Workspaces**: limit the sync to these workspaces, by workspace name, deployment name, or numeric workspace ID. This also scopes which metastores sync: only a metastore attached to one of these workspaces is synced, so narrowing the list removes the other metastores and their grants from C1.
    - **Exclude Workspaces**: workspaces to leave out of the sync, by workspace name, deployment name, or numeric workspace ID. A metastore attached only to excluded workspaces is not synced either, and C1 removes it and its grants.

  Fill in **Workspaces** or **Exclude Workspaces**, not both.
  </Step>
  <Step>
  **Google Cloud Platform and Azure Databricks customers only:** Enter your Databricks domain in the **Hostname** field, for example `gcp.databricks.com` or `azuredatabricks.net`. This is the domain your workspace URLs end with, not the URL of one workspace. Account Hostname is optional: the connector derives it from Hostname when unset.
    - For more on how to look up these values for GCP, see the GCP Databricks [REST API reference](https://docs.databricks.com/api/gcp/account/introduction) and [identifiers for workspace objects](https://docs.gcp.databricks.com/en/workspace/workspace-details.html) documentation.
    - For more on how to look up these values for Azure Databricks, see the Azure Databricks [REST API reference](https://docs.databricks.com/api/azure/account/introduction) and [identifiers for workspace objects](https://learn.microsoft.com/en-us/azure/databricks/workspace/workspace-details) documentation.
  </Step>

  <Step>
  Click **Save**.
  </Step>
  <Step>
  The connector's label changes to **Syncing**, followed by **Connected**. You can view the logs to ensure that information is syncing.
  </Step>
</Steps>

**Done.** Your Databricks connector is now pulling access data into C1.

</Tab>

  </Step>
  <Step>
  Search for **Baton** and click **Add**.
  </Step>
  <Step>

  If you're creating a new app, choose whether to link it to an application discovered from your identity provider: select **Yes** and pick the IdP application, or **No** to continue with just the connector.
  </Step>
  <Step>
  Set the connector's **Name** and, optionally, a **Description**.

  </Step>

### Step 2: Create Kubernetes configuration files

Create two Kubernetes manifest files for your Databricks connector deployment:

#### Secrets configuration

```yaml expandable
# baton-databricks-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: baton-databricks-secrets
type: Opaque
stringData:
  # C1 credentials
  BATON_CLIENT_ID: <C1 client ID>
  BATON_CLIENT_SECRET: <C1 client secret>
  
  # Databricks account ID (required)
  BATON_ACCOUNT_ID: <Databricks account ID>

  # Databricks credentials: OAuth
  BATON_DATABRICKS_CLIENT_ID: <OAuth client ID>
  BATON_DATABRICKS_CLIENT_SECRET: <OAuth client secret>

  # Optional: limit the sync to specific workspaces
  # (workspace name, deployment name, or numeric ID).
  # Also scopes which metastores sync: narrowing it removes metastores that no listed workspace is attached to.
  # Mutually exclusive with BATON_DATABRICKS_EXCLUDE_WORKSPACES — set one or the other, never both.
  # BATON_WORKSPACES: <workspace-a,workspace-b>

  # Optional: exclude specific workspaces from the sync
  # (workspace name, deployment name, or numeric ID).
  # Mutually exclusive with BATON_WORKSPACES — set one or the other, never both.
  # BATON_DATABRICKS_EXCLUDE_WORKSPACES: <workspace-a,workspace-b>

  # Optional: setting this enables incremental sync; leave it unset to disable it.
  # ID of the SQL warehouse used to query the system.access.audit log between full syncs.
  # BATON_SQL_WAREHOUSE_ID: <SQL warehouse ID>

  # Optional: include if you want C1 to provision access using this connector
  BATON_PROVISIONING: true
```

<Warning>
**`BATON_WORKSPACES` and `BATON_DATABRICKS_EXCLUDE_WORKSPACES` cannot both be set.** They are mutually exclusive, and a config carrying both is rejected at startup before any API call. Choose one.
</Warning>

<Note>
OAuth requires a reachable account API. If the account API check fails at startup, the connector fails validation instead of falling back to a workspace-only sync, even when `BATON_WORKSPACES` is set.
</Note>

See the connector's README or run `--help` to see all available configuration flags and environment variables.

#### Deployment configuration

```yaml expandable
# baton-databricks.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: baton-databricks
  labels:
    app: baton-databricks
spec:
  selector:
    matchLabels:
      app: baton-databricks
  template:
    metadata:
      labels:
        app: baton-databricks
        baton: true
        baton-app: databricks
    spec:
      containers:
      - name: baton-databricks
        image: public.ecr.aws/conductorone/baton-databricks:latest
        imagePullPolicy: IfNotPresent
        env:
        - name: BATON_HOST_ID
          value: baton-databricks
        envFrom:
        - secretRef:
            name: baton-databricks-secrets
```

### Step 3: Deploy the connector

<Steps>
  <Step>
  Create a namespace in which to run C1 connectors (if desired), then apply the secret config and deployment config files.
  </Step>
  <Step>
  Check that the connector data uploaded correctly. In C1, click **Apps**. On the **Managed apps** tab, locate and click the name of the application you added the Databricks connector to. Databricks data should be found on the **Entitlements** and **Accounts** tabs.
  </Step>
</Steps>

**Done.** Your Databricks connector is now pulling access data into C1.
